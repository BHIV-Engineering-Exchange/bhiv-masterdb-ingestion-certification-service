3. The New MASTERDB Position
MASTERDB should evolve from:
A system that stores and registers datasets.
to:
The governed central data platform through which BHIV applications can discover, register, access and reuse 
approved ecosystem data.
This does not mean every byte of BHIV data must physically live inside one database.
MASTERDB must support:
CENTRAL STORAGE
        +
REGISTERED EXTERNAL DATA
        +
REFERENCED DATA
        +
GOVERNED DATA ACCESS
Therefore:
Central data platform  one giant database.
Otherwise someone eventually dumps every CSV, telemetry stream, image and log into one PostgreSQL 
instance and calls it architecture. Humanity has suffered enough.

22. Definition of Done
MASTERDB is considered converged toward the BHIV Central Data Platform when:
* Every reusable dataset has a canonical identity.
* Applications can register datasets through standard interfaces.
* Applications can discover approved datasets.
* Applications can consume approved datasets through controlled APIs.
* Dataset ownership and provenance are known.
* MDU contracts are enforced.
* Dataset versions are traceable.
* Data movement is observable.
* Access is authenticated and authorized.
* Evidence is preserved through Bucket where applicable.
* Runtime integration exists through TANTRA.

--- Page 16 ---
* Production persistence exists.
* Backup/recovery exists.
* Failures are visible and recoverable.
* No application needs a private uncontrolled copy merely to reuse BHIV data.
* A real application can consume data produced by another application through MASTERDB.
* The entire flow can be demonstrated with evidence.
Final constitutional position
MASTERDB is the governed central data platform of BHIV. It provides the common data plane through which 
reusable ecosystem data can be registered, governed, discovered and consumed. It does not own semantics, 
orchestration, evidence authority or business decisions.
That is the role Kavy should now build toward.
